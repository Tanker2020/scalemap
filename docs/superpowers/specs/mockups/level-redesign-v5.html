▸ YOUR WASM QUESTION, STRAIGHT
WASM is the wrong lever here, and B doesn't actually need saving. three.js renders through WebGL — the GPU does the drawing; JS only orchestrates. Our globe's cost (and a 3D datacenter's) is draw calls and scene-graph overhead, not raw CPU math, and WASM only accelerates CPU math — the WebGL calls themselves would still cross the same JS boundary. The real fix is instanced rendering: one InstancedMesh draws 500 identical rack cabinets (or 5,000 LEDs) in a single draw call. With instancing + a frameloop that only renders on change, B comfortably handles hundreds of racks at 60fps in this same webview — the globe already proves r3f here. So the honest trade: B is viable, not perf-doomed; its true cost is build time and interaction fidelity (text, hover, drag inside WebGL all cost extra engineering vs DOM). WASM would only enter the picture for something like a physics-grade layout solver — which we don't have planned.

The rack model (your question, answered as a design decision): racks are OPTIONAL organizational containers. A new server lands in the free pool — standalone pods on the same floor, the natural home for the vps/cloud mental model — and you drag it into a rack only if racks are how you think. Rack capacity defaults to 8U, configurable 4–42 per rack (the cabinet renders exactly its contents and grows to its cap). An auto-arrange action racks the whole pool for people who want tidiness without the ceremony. Floor tiles grow a ring whenever racks + pods need the room; the camera refits. Option B lives on as github issue #23 with the full technical blueprint (instancing plan, perf budget, acceptance criteria) — same doc model, pure view swap.
